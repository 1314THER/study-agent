# StudyAgent 项目统筹介绍与讨论导航

> 整理日期：2026-10-25（Asia/Shanghai）。用途：作为深入讨论项目的总纲，统筹各份设计文档的分工、依赖与阅读顺序。
> 本文依据已有设计与实现核对文档整理，未重新统计数据库、运行模型评测或开展学生实验。功能状态与数量须结合各文档的核对日期阅读。

本文先建立整体认识，再进入各专题的详细设计。现有专题文档继续承担完整论述，总纲不替代其细节，也不将讨论范围缩减为功能宣传。

## 1. 项目是什么，要解决什么问题

**StudyAgent 是面向高中数学、以结构化解题步骤为基础的学习支持系统，目标是将作答诊断、针对性训练和长期学习记录连接起来。**

我们希望回答三个连续的问题：学生这次具体卡在哪里；接下来怎样学、练什么；经过帮助以后，能否在没有 AI 提示的新题中独立完成。

项目先用 AI 解题流水线形成可引用的参考步骤，再让批改、分步教学、变式生成和错题复盘共用这些结构。在此基础上，设计套路训练、试卷分析和长期学习记录，并逐步扩展教师、学校和教学助教 Agent 的协同。

“生涯”在本文档组中指学生跨课时、跨考试的长期学习历程。当前学科范围是高中数学，其他科目属于扩展方向。

## 2. 核心思路：从一次作答走向持续学习

四个基本概念分别承担不同作用：课时组织教学内容，知识点评价知识理解与运用，步骤表示可复用的解题操作，套路表示一类题的步骤组合。题目中的具体步骤，是这些操作在该题条件下的应用。

项目的整体设计可以沿下面的过程理解：

```text
题目 → 三阶段 AI 解题 → 结构化参考步骤
                              ↓
学生作答 → 步骤对照与问题定位 → 教学、补练或进一步诊断
                              ↓
                    无提示新题与延迟复测
                              ↓
                 更新学习记录，安排后续学习

教师利用授权学情调整教学；学校利用适当范围的证据支持教研。
教学协同 Agent 负责理解请求、调用工具、解释结果和跟进任务。
```

这是整体目标流程。三阶段解题、步骤批改、分步教学和参考题变式已有实现基础；自动诊断、跨层掌握度贯通、教师与学校协同等环节的完成程度不同。

贯穿各模块的设计是：**同一份步骤结构同时服务解题、批改、教学和训练，并将跨次作答作为后续判断的依据。** 是否比其他方案诊断更准、训练更有效，还需要比较与实测。

## 3. 各模块怎样共同构成系统

| 层面 | 承担的职责 | 与其他部分的关系 |
| --- | --- | --- |
| 教学概念与关系 | 定义课时、知识点、步骤、套路及其关联 | 为批改、训练、评价和推荐提供共同语义 |
| 单题能力 | 解题、批改、分步教学、出题、错因标定与查找 | 向套路训练、作业和整卷处理提供可复用能力 |
| 套路训练 | 组织母题、仿练、独立完成、变式与复查，决定后续练习 | 调用单题能力，结合学习顺序与知识准备，并产生长期证据 |
| 试卷与生涯 | 评价试卷、分析作答，积累知识与套路状态及长期能力记录 | 接收作业、练习和考试证据，为后续训练与教学提供历史参照 |
| 教学协同 Agent | 理解学生、教师和学校请求，查询证据、编排工具并解释结果 | 使用同一套业务能力和档案，按身份进入不同角色视角 |
| 教师与学校 | 组织课堂、作业、讲评、干预、教研和体系定制 | 教师将学情转为教学安排；学校维护适当范围的质量与课程规则 |
| 应用与接入 | 界定完整采用、传统教学增强，以及产品内置和外部宿主接入 | 教学采用程度与 Agent 宿主选择是两个独立维度 |
| 系统演进 | 利用纠错、人工维护、最新材料及学科适配改进系统 | 改进需要经过核对、验证和版本管理，再影响业务能力与记录 |

这里的分层表示设计职责，不要求实现为八个独立服务，也不表示各层已经完整建成。

深入讨论时，尤其需要保留以下区分：

- **教学关系与能力判断：** 知识点支撑步骤、步骤组成套路，但一次套路题通过不能直接证明所有前置知识都已掌握。
- **训练阶段与解题步骤：** 套路六步循环是训练组织方式；一道题中的步骤是数学操作，两者不是同一层级。
- **当次表现与长期状态：** 单题批改首先判断这次作答；长期掌握需要跨次、独立、新题与延迟证据。
- **试卷质量与学生表现：** 卷子是否符合模板，与学生为何在该卷失分，是两个评价对象。
- **沟通编排与业务事实：** Agent 负责使用工具和解释结果，实际评分、任务状态与记录由业务系统维护。
- **接入形式与教学模式：** 使用 DSH 或 WorkBuddy 不意味着学校已采用完整教学流程；在产品界面使用系统也可以只接入局部功能。

这些区分决定了文档之间的责任边界，也决定了哪些数据可以共享、哪些结论需要独立取证。底层体系版本、作答证据、身份权限和任务预算是跨模块问题，应由各模块共用一致规则。

## 4. 用一个学生案例串起模块

以下是目标体验的示例，不是已经完成的学生实验，也不表示所有环节都已接通。

一名学生在导数题中正确完成求导，却在根据导数符号判断单调区间时出错。系统首先对照学生原始作答，指出发生错误的步骤及其依据，保留其他正确部分。

随后需要区分：学生是不理解导数符号与单调性的关系，还是会判断但在符号表或计算中出错。证据不够时，通过概念辨析或局部小任务继续核实；不能只因整题答错就认定相关知识全部没有掌握。

确认局部困难后，可以讲解该步骤、安排针对性训练，再回到完整题目。训练完成后，用未见过的新题检查能否独立解决，并在间隔后复查。套路训练表现与知识理解分别记录。

教师据此判断是个别辅导、小组补充还是全班重讲。后续考试再出现类似问题时，可以结合此前记录提出解释和下一步验证目标。有手写时间线时，可进一步查看停顿和修改发生在哪里；停顿本身不能确定是心态或策略问题。

这个案例串起了单题、套路、生涯和教师端。深入讨论时，可以沿着每一环追问：需要什么输入，产生什么记录，谁负责确认，如何影响下一项任务，以及目前已有哪部分实现。

## 7. 不同讨论方向怎样调整顺序

| 对象 | 推荐路线 | 介绍重点 |
| --- | --- | --- |
| 整体方案讨论 | 本文 → 名词 → 单题 → 套路 → 试卷与生涯 → 角色协同与接入 | 先建立共同概念，再逐层讨论整个教学与学习过程 |
| 教师或学校试点伙伴 | 本文 → 两种模式 → 教师端 → 单题与试卷 → 学校端 → 实现状态 | 从熟悉的教学环节切入，讨论先接哪一项、需要什么数据 |
| 开发者或技术合作者 | 本文 → 实现状态 → 名词与关系图谱 → 单题 → 教学 Agent → MCP 适配 | 当前系统结构、数据口径、接口和可交付范围 |
| 研究者或评审 | 本文 → 单题与套路 → 相关工作 → 实现状态 → 待深化研究 | 可检验的问题、比较对象、现有证据与实验缺口 |

涉及具体模块时，可统一按“目标与对象 → 输入证据 → 处理与判断 → 输出及下一步 → 实现现状 → 待验证问题”的顺序讨论。这样既能展开细节，也能看清该模块如何与其他部分衔接。

## 8. 现有文档的完整性与使用方式

**这些文档已经适合支撑深入的方案讨论，原先主要缺少统一入口和跨文档关系说明。** 它们覆盖从单题到套路、整卷、长期学习、教师与学校的设计，以及 Agent 接入和系统演进。本文补上整体定位、模块分工、贯穿案例、状态摘要和讨论导航。

使用时可以将材料分为三个互相参照的部分：

1. **总纲：** 由本文说明项目整体是什么、为什么这样组织，以及接下来读哪份文档。
2. **专题设计：** 保留各文档的完整讨论，遇到相关模块时进入其细节，交叉引用其他专题。
3. **实现与研究对照：** 用实现文档核对当前能力，用相关工作和待深化研究讨论依据、差距与验证方法。

尚未确定的参数、数据集、算法和效果可以继续作为研究问题展开，不必为了介绍完整而预先给出确定答案。设计流程是否合理、工程链路是否接通、学生是否真正学会，也应分别讨论。

现有 [汇报 PPT 逐页脚本](汇报PPT-逐页脚本.md)有演讲素材，但其中对其他产品和传统教学的概括，如“伪个性化”“不知道错在哪一步”，需要逐项核对与收敛，不能直接作为研究结论引用。深入讨论以专题文档及可核对的证据为依据。

分享时保留文档的相对目录结构，便于文内链接正常跳转。设计文档组从本总纲开始；安装、运行和部署另读仓库 [README](../README.md)，实现细节与设计目标分别查阅。
