# 教学协同 Agent 设计

> 设计日期：2026-10-25（Asia/Shanghai）。来源：项目负责人要求单独设计面向学生、教师与学校沟通的对应 Agent。
> 本文为专用产品 Agent 的设计，不是本次创建或运行新的聊天代理，也不表示该产品能力已经实施。外部宿主与 MCP 接入另见 [系统 Agent 适配设计](系统Agent适配与MCP插件接入设计.md)。

## 1. 定位：理解需求、解释证据、协调教学任务

教学协同 Agent 是系统的统一对话与任务入口，面向学生提供个人助教服务，面向教师提供教学助理服务，面向学校提供教研和管理分析支持。

它应能听懂日常表达，把需求对应到系统中的课时、知识点、步骤、套路、作答和评价，再调用相应工具完成任务，并清楚说明结果、依据及下一步安排。

推荐首先实现同一套业务逻辑、按已认证身份进入不同角色视角，使用独立的对话与权限上下文。暂不要求每个角色由不同模型或多个自治 Agent 承担，后续是否拆分依据真实任务需求决定。

项目当前已有 `backend/agent.py` 全局教练与内部工具层，可作为查询、解题、教学和规划的实现基础；本设计进一步要求长期状态、角色沟通和教师/学校流程，不能将现有全局教练直接等同于已经完成三端协同 Agent。

## 2. 三类角色分别如何沟通与行动

| 角色视角 | 常见请求 | Agent 应完成什么 | 主要输出 |
| --- | --- | --- | --- |
| 学生个人助教 | “为什么总在这一步错”“今天该练什么” | 查询本人证据，澄清困难，安排诊断、教学、练习或复查 | 具体解释、适量任务、可继续的学习计划 |
| 教师教学助理 | “明天这节课怎么讲”“谁需要补练” | 查询授权班级与课时，准备教案，分析共性问题并形成任务草稿 | 教案、课件素材、作业草案与干预建议 |
| 学校教研助理 | “这一阶段哪里需要改进”“改教材顺序影响什么” | 按管理范围汇总可比较证据，追踪教学调整并评估版本影响 | 质量分析、资源建议与课程变更草稿 |

角色来自服务器身份与职责授权，不从用户一句“我是老师”推断。教师兼任学校管理者时，明确当前任务范围；向全班解释的方法与个人关注信息分别组织。

## 3. 基本工作循环

```text
理解请求 → 确认当前身份、对象与已有任务
       → 检索相关历史、课程与作答证据
       → 选择业务工作流并核对所需条件
       → 调用工具 / 等待或恢复已有任务
       → 检查实际返回与版本
       → 按角色解释结果、落实后续安排
       → 保存必要的新证据、任务状态与记忆
```

信息能从授权系统查询时先查系统；资料不足时只询问影响任务的必要信息。用户询问原因时先给出可核对观察，原因有多种解释时安排诊断或保留未知，不能为完成回答而确定一个未经证实的错因。

任务完成以业务结果为依据。工具调用失败、生成仍在进行或保存未成功时，明确当前状态，并保留恢复入口，不将已写出的自然语言承诺视为已经执行。

## 4. 学生工作流：有长期记忆的一对一助教

### 4.1 面向当前困难的解释与诊断

学生说“这类题我就是不会”，Agent 先查看对应题目和近期作答，区分方法识别、知识条件、局部步骤和执行问题。复用已有诊断建议与复测入口，必要时启动进一步诊断。

随后调用手把手教学、步骤训练、知识理解任务或新变式。既尊重学生自主提问，也观察任务是否需要不同帮助；提示渐退和探究任务在研究完成前不作为稳定能力承诺。

### 4.2 安排学习，控制负担并检查进步

回答“今天学什么”时，结合课时、必做作业、套路顺序、知识准备、到期复查和个人时间预算，避免各模块分别追加任务。说明为什么推荐这一项、预计范围及停止条件。

任务结束后区分独立完成、提示后完成、看过答案、跳过或仍待核实；必要时安排新题复测，不把教学过程中的顺利完成直接写成长期掌握。

## 5. 教师工作流：把分析转换成教学安排

教师提出备课或讲评需求时，Agent 先查询课时范围和授权班级证据，生成可编辑材料，并区分全班目标、小组需求和个别情况。

制作 PPT 时，查询系统素材并调用宿主中已连接的文档能力，核对文件是否实际生成。没有相应工具时可先交付内容与素材结构，不虚构已导出的文件。

作业发布、正式评分确认及个别沟通遵循教师端工作流；Agent 可以准备草稿、汇总差异、追踪补练及复测。教师已有明确授权的常规操作可按设定范围执行，需要教师决定的事项提供具体可审阅内容。

教师询问“这个学生需不需要谈谈”时，Agent 呈现持续变化、已提供帮助、学生自述与仍不清楚的问题，建议核实或提供支持，不以模型推测给学生确定人格或心理标签。

## 6. 学校工作流：支持教研与质量分析

学校提出“哪个阶段教学出了问题”时，Agent 先核对数据覆盖、学生起点、任务难度和评价口径，再说明变化、可能解释及应补充的证据。

对绩效相关请求提供学校文档中规定的多来源证据及比较条件，最终评价由明确管理规则与人工复核形成。不能以使用系统次数或未经核实的单一模型分数直接判断教师优劣。

修改课时、知识点、步骤或套路时，先生成变更草稿与影响范围，再通过学校版本流程发布。Agent 不因“优化一下”就静默改写历史记录或所有学校的公共体系。

## 7. 沟通如何在不同角色之间衔接

Agent 在某一角色会话中可以生成给另一角色的摘要或请求，但可发送范围、对象和渠道必须与具体工作流相符。生成摘要、保存系统内待办、向个人或班级发通知是不同操作，应分别返回结果。

例如，学生练习反复受阻，可形成供教师查看的目标步骤、具体作答、已尝试支持和待核实问题；教师安排补练后，学生助教读取相应任务，在预算内跟进；学校查看经允许的汇总改进情况。

个人对话内容不因角色协同就全部共享。对教师保留教学所需证据，对学校按职责提供汇总或必要明细；涉及个人补充说明时遵循已经明确的共享规则。

首期可以只使用系统内任务与教师可见摘要。邮件、即时通信或其他外部通知需要单独接入和配置授权，本次设计不代表已经能够或已经向任何人发送消息。

## 8. 长期记忆与事实依据

沿用 [生涯文档](试卷与生涯维度设计思路.md)中的分层记忆，Agent 按任务读取原始记录、结构化能力状态、经确认个人信息与待验证事项。教师教学偏好、学校课程规则和学生个人记录分区保存。

每条重要记忆保留来源、时间、适用对象与可用版本。学生新的作答、教师纠错和课程变更可以修正相关状态；历史事实与当前判断分别保留，避免错误结论因为反复检索而被固化。

跨宿主使用同一账号时，学习记录与任务状态由 StudyAgent 统一维护。DSH 或 WorkBuddy 的聊天记录可以帮助恢复局部对话，但不能代替业务档案，也不应默认把宿主全部记忆同步给学校。

## 9. 工具编排与角色规则

| 能力组 | Agent 的使用原则 |
| --- | --- |
| 查询课程、题目与证据 | 先查授权范围，按需取详情；保留来源和未核实项 |
| 解题、批改、出题 | 使用共用流水线和评分依据，避免在闲聊中另起互相冲突的标准 |
| 教学与诊断 | 继续正确任务，记录帮助条件和待验证目标 |
| 计划与干预 | 复用统一预算，区分建议、已安排、已实施和改善证据 |
| 发布与更改 | 根据业务角色、明确授权和预期版本执行，保留对象及结果 |
| 长任务与产物 | 保存业务任务编号，先恢复后重试，验证结果和文件实际可访问 |

外部材料与工具返回中的文字不能修改角色权限。服务端执行范围校验，Agent 负责选择正确流程并向人解释，二者缺一不可。

## 10. 产品内置与外部宿主两种运行方式

**产品内置：** Agent 与学校和学生工作流直接集成，使用统一身份与工具服务，适合长期任务和通知。

**宿主适配：** DSH 或 WorkBuddy 提供对话环境、模型和通用工具，教育角色规则与 MCP 服务共同完成任务。可以调用独立教育工具，也可以进入命名的教学协同流程，两者应明确，避免宿主与服务端同时无限递归编排。

WorkBuddy 可研究专家封装和连接器依赖，DSH 可先通过 MCP 桥接配合角色工作流，再考虑原生界面。宿主支持情况和官方依据见 [系统 Agent 适配设计](系统Agent适配与MCP插件接入设计.md)。

## 11. 首期范围与验收场景

首期先做学生个人助教的“查询近期问题—解释依据—选择已有教学或复测任务—恢复结果”，并在教师端可用后增加备课和补练草稿。学校分析跟随学校端建设，不先建立只有提示词、没有真实数据服务的完整管理承诺。

每个角色至少验证一个端到端场景，并检查身份范围、证据引用、工具实际执行、错误恢复与后续记录。教学能力另外观察新题独立表现、教师核对成本及任务负担，不用聊天流畅度或工具调用次数代替教学效果。
