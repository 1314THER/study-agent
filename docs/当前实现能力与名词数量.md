## 2. 共用技术基础：现有大模型 API、提示词和结构保护

当前这四项单题功能的主要模型实现方式是：**调用现有公开 API 大模型，配合任务提示词，再通过正则提取、JSON 解析、字段检查与后端规则处理输出。** 本次核对的主链路没有项目自训练或微调模型的环节。

| 层 | 当前实现 |
| --- | --- |
| 模型调用 | `backend/solver.py` 的 `call_deepseek`，通过 HTTP 调用配置的 `/chat/completions` 接口；默认服务为 DeepSeek |
| 模型路由 | `backend/settings.py` 提供运行时老师配置；不同阶段可以使用不同模型与思考设置，具体值以运行时配置和调用参数为准 |
| 提示词 | `backend/prompts/solver.md`、`verifiers/`、`formatter.md`、`grade.md`、`teach_format.md`、`teach_check.md`、`generate.md` |
| 术语数据 | `backend/categories.yaml` 与 `backend/steps.yaml` 提供知识点和步骤定义；板块校验提示词承载相应步骤要求 |
| 输出保护 | 固定文本字段正则解析、JSON 片段提取与 `json.loads`、步骤完整性和评分字段检查、有限重试、带标记的失败结果 |
| 确定性处理 | 难度聚合、评分上限、部分客观题答案匹配、候选去重与相似度排序、教学会话推进和存储 |

`call_deepseek` 还预留本地调用器分支；主链路仍以配置的公开 API 为依据。正则和 JSON 检查用于保护结构，不能证明推导或答案的数学正确性。

## 3. AI 解题：已实现的三阶段流水线

主要代码：[solver.py](../backend/solver.py)。

1. `step_solver_only`：调用 Solver 提示词，输出解答、板块与校验模板信息，并识别不能解答或题目异常等状态。附题图时使用图片消息路径。
2. `step_verify_all`：根据题型及 Solver 指定模板选择 Verifier 提示词；将输出按块和步骤解析，形成 `chunk_results[].steps[]`，保存标准过程、详细过程、知识点等字段。
3. `step_final_check` / `_call_formatter`：要求 Formatter 输出 JSON，并给步骤补充五维难度；后端检查结构并聚合难度，随后可准备几何演示资料。

核心步骤字段包括 `chunk_id`、`step_number`、`title`、`step_level1`、`standard_writing`、`detailed_writing`、`knowledge_point`、`step_difficulty`。其中 `step_level1` 是历史字段名，实际承载二级具体步骤名，不应仅凭名字理解其层级。

代码会校验预定义步骤名，非法二级步骤名会被清空；能由合法子步骤识别父步骤时会归一化标题，同时保留未归类步骤的可读标题。当前实现并非所有解析步骤都被强制映射成 YAML 中的唯一 ID。

Formatter 失败时，在有 Solver 原始输出的条件下会重跑一次 Verifier，再试 Formatter；仍失败则保留可用步骤，返回 `error=formatter_failed`、`formatter_fallback=true` 等标记。不能把兜底结果当作已经通过最终校验的解析。

**与设计的关系：** 三阶段、分步结构、标准/详细过程及输出保护均已实现；“更符合试题要求、更易理解”是这套结构的设计目标，尚未在本次工作中进行对照评价。

## 4. AI 改题：参考步骤与学生作答的对齐

主要代码：[grade.py](../backend/grade.py)，提示词：[grade.md](../backend/prompts/grade.md)。

- 大题从已有解析收集标准步骤，为每步构造如 `1-2` 的局部编号，将原题、学生作答、标准步骤、最终答案及可选评分点一起交给模型。
- 模型返回逐步状态：`correct`、`partial`、`missing` 或 `not_applicable`，并可输出作答原文证据 `answer_evidence`、错因、原因置信度与批改置信度。
- 提示词明确要求：步骤缺失不能直接推断为知识或思路错误；原因不明时保留未知；学生采用不同思路时独立判断数学正确性。
- 后端限制步骤编号与状态取值，过滤非法错因，限制分数范围；有确认评分点时校验其分值并聚合，证据或置信度不足时提示复核。
- 选择题、多选题、填空题当前主要走答案匹配路径；部分填空等价关系不能确认时返回待复核，不提供与大题相同的逐步 AI 诊断。

当前已具备“按参考步骤定位并附证据”的技术结构；学生作答到步骤的对齐仍由模型完成，后端尚不能自动证明引用片段真实、归因正确或没有遗漏。不能直接把字段齐全等同于“完全避免 AI 猜测”。

## 5. 手把手教学：步骤任务、检查模型与会话状态机

主要代码：[teach.py](../backend/teach.py)，提示词：[teach_format.md](../backend/prompts/teach_format.md)、[teach_check.md](../backend/prompts/teach_check.md)。

1. 优先查找已有解析；没有可复用解析时运行三阶段解题流水线。
2. 从参考解析构建教学步骤；缺少引导语时，`_fs` 使用模型为步骤生成 `step_prompt` 和 `step_answer`，失败时以标题与标准过程兜底。
3. 每轮普通回答由 `teach_check` 提示词检查，模型主要接收原题、当前步骤问题、预期答案与本轮学生回答；正确则推进，错误或部分正确则留在当前步骤。
4. 跳过、请求提示、查看答案等命令由规则分支处理；当前普通文本提示主要从本步答案中截取逐渐增多的内容，几何题可释放对应图形提示。
5. 会话保存当前步骤、回答次数、消息、逐步结果及正确/错误/跳过/看答案统计，并使用数据库持久化；结束时可写入步骤错因记录。

仓库中虽有 `teach_chat.md` 描述更完整的对话式教学提示词，当前 `_do_chat_turn` 主路径采用的是预生成步骤问题、`teach_check` 检查和后端规则推进，不能仅根据该提示词文件就宣称每轮会完整分析全部对话历史。

**当前可观察的是本题、本步骤的作答表现。** 完整的跨题步骤掌握模型、可靠的长期知识状态估计，以及自动回溯前置知识后的补课闭环，不能由这份会话状态直接推出。

还需注意两处记录边界：跳过分支会在 `step_results` 中写入 `correct=true`，同时单列跳过统计，因而不能只统计 `correct` 判断掌握；请求文字提示分支没有独立的逐步提示次数或“提示后答对”字段，仍需结合消息记录。看答案后答对也不等同于独立完成。

## 6. AI 出题：围绕参考题生成并重新解答

主要代码：[generate.py](../backend/generate.py)，提示词：[generate.md](../backend/prompts/generate.md)。

当前已实现的主要出题路径是**基于一份题库参考题的变式生成**。参考题不要求必须登记为母题，但会向模型提供题干、题型、板块、步骤结构、难度，以及已保存的错误步骤和学生错误作答。

生成模型先输出候选题干和设计目标，不直接生成最终参考解析。候选经过批内去重与题库重复检查，再分别进入 Solver → Verifier → Formatter。失败、解析结构不完整或最终校验失败的候选被拒绝；通过的题目保存为 `ai生成`，并记录参考题 ID。

通过候选随后按与参考题的匹配程度排序，当前启发式评分由难度接近程度、步骤标题序列相似度、知识点重合度、题型一致性组成，权重依次为 45%、30%、15%、10%。这项分数是在通过候选保存后计算和排序的，当前没有以最低匹配分作为硬性接收门槛。

**与设计的差距：** 已有步骤和参考题约束，也有重新解题检查；步骤名称相近不能证明方法同构，模型给出的可解判断不能替代形式化验证。当前路径没有针对每名学生已学课时的硬性过滤，也不能将它描述为已经完成任意单步骤专项出题。

## 7. 当前难度实现与“步骤默认难度”设计的区别

主要代码：[difficulty.py](../backend/difficulty.py)，评分提示词：[formatter.md](../backend/prompts/formatter.md)。

当前 Formatter 针对**题目中的每个实例步骤**输出五维评分：非常规程度、计算量、分类讨论、知识广度、条件转化难度，每维 0–3。后端确定性聚合为块与整题难度，默认总分上限为 15；权重、上限与等级阈值可配置。

代码另有人工填写的套路难度 0–3，匹配到正式套路时可与执行难度合成综合等级。这些是当前实现口径。

负责人提出的“为每个结构化步骤提供默认难度，再结合具体题目的计算量、偏离母题的非常规程度等调整”，属于后续设计。当前 `steps.yaml` 是步骤名称层级表，没有逐项默认难度数据；本次未发现该基准表驱动四项功能的完整实现。实例步骤五维评分与步骤词表默认难度不能混称。

## 9. 已有主动诊断相关能力与复测链路

代码依据：[student_analysis.py](../backend/student_analysis.py)、[诊断数据契约](../backend/student_analysis_types.py)、[学情前端](../frontend/student-analysis.js)、[相关测试源码](../tests/test_student_analysis.py)。本次静态核对，未运行模型调用或这些测试。

- `_RulesDiagnosticEngine` 调用 `build_report`，从已确认考试与作答中整理知识、套路、基础题表现及时间风险线索，保留支持证据、相反证据、可能原因及 `cause_confirmed=false`。
- 报告返回 `recommendation` 和 `validation_target`，并给出最多三项优先建议。例如，通过相近难度的限时与不限时新题，核实知识、计算和时间策略等可能原因；通过口述方法条件与变式，核实方法选择和执行。
- 考后问卷补充学生自述的卡题、跳题、检查、信心与状态；这些属于自述证据，不是客观笔迹时间戳或已经确认的错误原因。
- `/student-analysis/attempts/{attempt_id}/questions/{question_id}/followup` 可关联题库练习记录，并用题干哈希排除原题重做。重新生成报告时，可把所关联记录加入诊断发现并更新证据级别。
- 前端已经展示训练建议、复测目标和关联入口；不是只有诊断字段而没有使用入口。

因此，项目已有“发现问题—提出验证目标—关联补测证据”的主动诊断基础，不应整体列作遗漏功能。当前主要由规则生成建议、人工选择并关联练习；尚未发现按候选原因自动生成区分性小题、逐轮自适应选择下一诊断题及自动停止的完整链路。

还需保留实现边界：复测接口核对记录存在及是否为不同题干，未完整核验该题是否命中验证目标、是否无提示或未看答案；报告将关联记录加入 `supporting_evidence` 并标为 `followup`，并不自动证明某个原因被证实。后续增强应区分复测支持、反驳与仍不确定。

## 10. 纠错回溯与低门槛输入的已有基础

`student_analysis.py` 的 `_report_source_snapshot` 保留源记录与修订信息，`_report_stale` 可识别来源版本变化；这是报告失效检查的基础，不等于参考解析更改后全部批改、推荐与生涯记录已经自动重算。

学生答卷模块已有图片/PDF 提交、识别片段核对、未匹配内容分配与失败重试。Apple 客户端的 [QuestionView.swift](../apple/StudyCoach/Sources/StudyApp/QuestionView.swift)和 [SQLiteStore.swift](../apple/StudyCoach/Sources/StudyCore/SQLiteStore.swift)已有 PencilKit 笔迹保存、本地草稿及按账号与服务器分区的缓存；[StudyModel.swift](../apple/StudyCoach/Sources/StudyApp/StudyModel.swift)在网络提交前保存请求编号以支持同一操作重试。

这些基础不等于完整的跨端离线同步、逐笔修改事件日志或云端模型离线运行。6—8 项研究应在既有基础上继续设计，避免当作全部从零开始。详细方案见 [待深化功能研究](待深化功能研究-提示干预与可靠接入.md)。
