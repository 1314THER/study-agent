01 / 系统边界

总体架构：让每个箭头都有数据含义

端侧采集输入；领域服务确定身份、权限和事务；Agent 决定查什么、调用什么；模型只在当前角色上下文中提出结果；数据库负责事实、版本与可恢复状态。

拟议架构
任务 / 请求 检索证据（R） 提案与工具返回 事实 / 修订写入（W）
A

入口先确定范围

身份由认证服务给出，课程、题目、任务和量规按当前版本绑定。LLM 不能自行声明“我是教师”或扩大可读学生范围。

B

两路检索，再读当前状态

RAG1 找“教学上可用的依据”；RAG2 找“这个人实际发生的事实”。DB3 提供有版本的当前解释。三者带出处进入 EvidenceBundle。

C

模型提出，服务核验并提交

模型返回 GradeDraft、TutorTurn 或 WikiPatch 等结构化提案；服务核对权限、引用、对象版本、阶段与预算后，再将正式事实和 outbox 事件写入 PostgreSQL。

D

事件驱动跨时间闭环

事件消费者重新取证，LLM 提出学情更新；服务比较 base_revision 后保存 DB3 新版本，再刷新相关任务和班级视图。失败可按事件位点恢复。

研究重点系统是否成功，要看业务任务的最终状态、依据和副作用，而不是只看模型回答像不像正确答案，也不是只看工具 JSON 能否通过解析。
02 / 数据底座

三类数据库职责分开，证据再由 LLM 协作

“数据库”不是一个向量搜索框。教学定义、发生过的事实和系统目前对学生的判断，更新节奏和可信等级都不同，因此分开保存、按对象版本关联。

物理选型方案
DB1SQLite · 只读发布

教学依据库

回答“在这个省份、教材和课堂进度下，什么依据可用”。

  • 课程、知识前置、方法及适用 / 排除条件
  • 题目、多条解法、规范操作、步骤与评分量规
  • 来源、审核记录、稳定 ID 与 CourseRelease 版本
编辑侧独立 SQLite 工作库，保留提案和审核历史。运行侧发布为只读 SQLite 文件；学生运行不依赖内容工作台在线。
关系表 / nodes & edges → FTS5 词法检索 + 公式归一化候选 + 语义候选
DB2PostgreSQL · 事务事实

学习与教学事实库

回答“学生 / 教师实际做过什么，发生在何时、哪个版本”。

  • 题目与作答修订、原始媒体引用、笔迹和时间
  • 帮助暴露、提示确认、评分版本、教师复核与任务
  • model_runs、jobs、outbox、consumer_receipts
类型关系表保存约束和关联；JSONB 放有版本的扩展载荷。媒体放在受控文件 / 对象存储，PG 只保存 asset_ref、hash、归属和权限。
SQL 取精确字段 + 原文片段检索 + 事务 / 幂等键
DB3PostgreSQL 修订元数据 + Wiki

当前学情与可读状态

回答“目前有哪些有依据的理解，哪些仍未知，需要怎样验证”。

  • 学习进度、知识 / 方法 / 步骤表现、目标和未知
  • 每条判断标记 observed_fact、inference、self_report 或 human_note
  • 保存证据、反证、旧版本、base_revision 与 supersedes
可读层Markdown 与结构化 blocks。修订层PG 保存 Wiki revision、sync cursor 与 conflict；可与 DB2 共用 PG 实例，但逻辑 schema 和权限边界分开。
DB2 正式事件 → Agent 取证 → LLM 提案 → 服务提交新版本

教学关系怎样被搜索

先用课程 release、审核状态、学段和任务目标做硬过滤；再以词法、公式结构和语义召回候选，沿“知识前置 → 方法 → 有序步骤 → 例题”扩展。最后回表验证来源、权限与版本，才把片段交给模型。向量相似度只负责候选排序，不负责评分或事实判定。

课程 / 权限硬过滤↓FTS5 + 公式 token + 向量候选↓关系扩展 / 重排↓回表校验 / EvidenceBundle
向量索引状态

候选方案是复用 PostgreSQL pgvector 保存派生向量，让 DB1 教学片段和 DB2 私人证据分 schema / 权限域管理；这是待验证选型，不写成已上线。关系结构首版由 SQLite / PostgreSQL 强类型关系表表达，不为技术名词额外引入图数据库或消息中间件。

模型与数据库的调用协议LLM 不拿整库连接，不把聊天记录当数据库
  1. 身份与任务认证服务给身份、班级范围、课程与任务版本；TA 生成 QueryPlan。
  2. 受控取证RAG1 查 DB1，RAG2 查 DB2 精确事实与原文片段；再读相关 DB3 版本。硬过滤由程序执行。
  3. 编译上下文按角色规则、任务合同、课程约束、检索证据、不可信原始输入五层组装；记录来源和 token 清单。
  4. 生成提案LLM 只做当前角色的语义工作，例如找首错、给有限提示或提出 WikiPatch。
  5. 服务核验Tool Gateway 检查 schema、权限、证据引用、对象版本、业务阶段和预算；数学正确性另行核验。
  6. 事务提交领域服务写正式事实和 outbox；后台消费者按 event_id 去重，再触发 DB3 学情更新。

RAG1 / RAG2 中的词法、公式、向量索引均是从源对象派生的搜索结构，不能代替 DB1 / DB2 作为事实来源。

03 / Agent 执行机制

新 Agent Loop：围绕可恢复任务状态运行

旧原型已有简单工具轮询。研究方案要具体到状态、证据、提交和恢复：Agent 不是聊天里反复问模型“下一步做什么”，而是一个带任务合同、预算、权限和持久事件位点的执行器。

拟实现协议
01接收校验身份、输入版本和完成条件
02取证QueryPlan → DB1 / DB2 / DB3
03编译角色上下文、引用、预算
04提案模型提出动作或请求补充
05校验权限、schema、版本、业务规则
06执行受控工具与领域服务
07观察 / 恢复核验真实返回，识别已提交副作用
08提交 / 停止完成、等输入、待复核或失败
RunState 持久字段

恢复时从任务事实继续，不靠模型 KV cache

  • task / run id
  • 课程与输入 revision
  • 当前 phase
  • EvidenceRef 清单
  • 动作与实际返回
  • 剩余调用 / token / 时间
  • 待学生输入 / 教师复核
  • commit 记录 / event cursor
四类逻辑角色，按任务隔离上下文与工具角色不是四个必须独立训练的模型
01 / CLEAN

保真识别

读取题图、笔迹或文本，返回转写片段、位置和歧义候选；不读取参考答案，也不擅自修正学生的数学错误。

图像 / 笔迹 → 可信转写
02 / SOLVE

求解与核验

结合题目版本、课程范围和 DB1 依据生成候选解法，检查条件、边界与合理异解，记录实际使用的操作。

题目 + 课程依据 → 解法提案
03 / SOCRATIC

批改、提示与范围

按不同 task contract 执行 GRADER、TUTOR、SCOPE、PAPER_REVIEW；角色间隔离参考答案、学生状态和提示等级。

证据 + 量规 → 有边界的教学回应
04 / TA

协调与学情维护

持有 RunState，决定补查、调用哪个角色、如何恢复，以及何时提交或等待；通过工具服务取证，不直接写 SQL。

任务状态 → 可验证的动作序列

同一个 4B / 9B / 27B 权重可以按角色加载不同 system contract 和工具权限，也可使用独立适配器；每次运行记录实际权重 / adapter。OCR、embedding、reranker、外部求解器若参与，也必须在运行账中单列。

1

单任务循环

接收一项具体请求，补查证据、提出动作、校验返回、提交结果或说明为什么等待。按幂等键避免重试造成重复写入。

一次答疑、批改或组卷
2

跨时间教学循环

作答 → 批改 → 分级提示 / 训练 → 无提示新题 → 延迟复测。提示后会做是“辅助完成”，不直接记成独立掌握。

多次任务与学生交互
3

后台状态维护循环

正式事件 → 重新取证 → LLM 提交语义 patch → base_revision 校验 → DB3 新版本 → 更新受影响任务。失败可重放，旧判断可撤回。

事件消费者异步执行
提交边界模型输出先保存为提案。最终分数、对象关系、权限、版本与事务由代码负责；调用成功不等于任务成功，JSON 合法也不等于数学正确。
04 / 完整业务场景

用一道闭区间最值题走完整条数据链

这里展示总体架构中的一个场景实例：学生写错后，系统怎样定位边界条件、分级引导、记录提示暴露、更新学情，再验证新题。图中状态 ID 是协议示意，不是已发生的模型调用。

构造案例
题目与当前作答

设 a ∈ [0, 3]，f(x) = x² − 2ax + 1，且 x ∈ [0, 2]。求最小值与最大值随 a 的变化。

学生片段 seg-2：“配方得 f(x) = (x − a)² + 1 − a²，所以所有 a 的最小值都是 1 − a²。”
本例要发现只有当顶点 x=a 落在定义域 [0,2] 时，最小值才能直接取 1−a²。
最小值
0 ≤ a ≤ 21 − a²2 ≤ a ≤ 35 − 4a
当 a=3，顶点 x=3 不可行；区间端点 x=2 给出 f(2)=−7，而学生公式给 −8。
最大值
0 ≤ a ≤ 15 − 4a1 ≤ a ≤ 31
在闭区间上比较两个端点值 f(0)=1 与 f(2)=5−4a；本例不使用尚未学习的导数。

一次任务的 30 个交互节点

先看 RAG、批改和提示；再看事件、WikiPatch 与独立复测。

打开原尺寸 ↗

图 2a　原图、识别、作答修订、双路检索、GradeDraft、正式评分与 TUTOR 提示。

输入

保存原始材料，再做保真识别

照片或原生笔迹先进入受控资产目录；PostgreSQL 写 AttemptRevision、asset_ref 和学生原文。CLEAN 输出转写、区域和歧义；关键符号不清时请求确认，不替学生把错误式子改对。

取证

分别查询 DB1 教学依据、DB2 学习事实

RAG1 返回顶点可行性、闭区间单调性 / 端点比较、量规和 CourseRelease；RAG2 返回相关作答、提示暴露和独立复测事实。DB3 回传旧状态及 revision；无历史就明确“未知”。

批改

GRADER 只提交带引用的诊断提案

SOCRATIC.GRADER 引用 seg-2，指出“所有 a”推广过度，并用 a=3 作为反例。把“没有检查定义域”作为本次可观察缺失；究竟是遗忘、分类讨论不熟还是书写省略，暂时保留为候选解释。

引导

独立编译 TUTOR 上下文，不泄露完整解答

只传当前目标、学生片段、允许的提示等级、已暴露内容和最小参考片段。例： “最值点一定在允许的 x 范围内吗？” 服务保存 TutorTurn；提示实际展示后另记 HintExposed。

回流

事件驱动更新，但辅助订正不算独立掌握

学生提示后订正形成新 response_revision，并带 assisted 条件。TA 读取 DB1、DB2、旧 DB3 后让 LLM 提出 WikiPatch；服务校验证据、反证和 base_revision，再写 DB3 新版本。

验证

排除已暴露题族，生成下一项独立任务

规划器读取硬性作业、复习期限与时长预算；检索避开已暴露题及近亲题。新题先由 SOLVE 独立求解 / 核验，再在无提示条件下记录真实表现。结果支持、收窄或撤回旧判断。

数据库中的对象链AttemptRevision → HelpExposure → GradeRevision → outbox event → LearnerStateUpdate → TaskPlanRevision → IndependentCheck
人工纠错分支

若教师发现 OCR 漏掉了正确的区间讨论，系统追加新 GradeRevision 与 GradeSuperseded 事件，撤回不受支持的 DB3 判断，重评相关任务和班级汇总；原稿与旧修订都保留。

案例说明的是拟议数据协议与数学边界，不是真实学生、教师实验或新 Agent 的实跑轨迹。后续必须用脚本回放正确异解、重复 / 迟到事件、教师纠错和服务故障分支。

05 / 学生与班级教学

长期学习和班级教学，具体落在同一条修订链上

长期学情不是把历次对话压成一段摘要；班级报告也不是把个人分数取平均就结束。每个结论需要保留观察范围、帮助条件、适用版本和可下钻的原始依据。

业务闭环
学

学生长期学习

  1. 新作答、提示、订正、独立复测分别成为事件。
  2. 状态按知识 / 方法 / 步骤与证据范围更新；一次提问或答对不直接推出长期掌握。
  3. 规划器从必做、到期复习与候选训练中分配时间，冲突时解释替换或延期。
  4. 教师或后续新题推翻旧判断时，系统保留历史并重算后续任务。
班

教师与班级教学

  1. 教师确定教材 / 校本 CourseRelease、课时目标、题目版本、量规和帮助规则。
  2. 学生提交与修订共享 task_id；缺交、未识别、未参与分别计入分母规则。
  3. 班级汇总显示共性错误、范围边界、样本量和未观测人数，可回查到原作答与量规。
  4. 教师复核后产生正式 GradeRevision；受影响的个人状态、分层任务与班级视图同步重算。
有历史

只导入授权材料，保留来源、原始时间和未知范围；不把旧摘要当作已验证事实。

没有历史

可以选择经校准的短测建档，也可以直接开始使用；系统逐次记录证据，不强迫学生先完成全科测评。

中途加入

按入组日期和实际观察窗口做班级比较；未参与、缺材料和未掌握分开统计，不把“没数据”补成零分。

06 / 小模型与 LoRA

让 4B、9B、27B 在同一系统里接受检验

LoRA 不是项目创新结论，而是适配手段。研究重点是：同一套数据库、证据编译和工具协议下，业务适配能否让不同规模模型更可靠地完成教学任务、并在资源受限环境运行。

效果待测
主线模型档9B · 系统核心评测档

优先回答：在三库、Agent Loop 和业务 LoRA 协同后，9B 能否覆盖已定义的解题、批改、提示、状态维护和教学协作任务；逐类报告失败，不以单一均分掩盖短板。

4B

部署资源下限

测低资源下的工具遵循、检索证据使用和有限提示能力，明确哪些任务需要拆分、确定性工具或人工复核；不预设它能独立承担所有任务。

9B

重点系统主线

固定系统条件比较基座模型与 LoRA 适配模型，重点观察核心业务任务覆盖、重大错误、成本和校内断网运行。

回答：小模型能否覆盖完整定义的核心流程？

08 / 产品与部署边界

B 端守住学校数据边界，C 端降低开始使用的门槛

两种模式共享任务、课程、证据和修订契约，数据范围、身份来源与模型调用策略不同。部署选项应让学校和学生能按需要选择，而不是把全量学生信息默认送去外部 API。

双模式设计
使用方实际需求问侠的交付边界模型与数据
学校 / B 端课程校本化、班级任务、教师复核、教学统计、可审计数据链。FastAPI 模块化单体起步；学校私有网络部署；学生端与教师端共享任务 ID、版本和权限规则。核心工作流不以商业模型 API 为前提；本地 PostgreSQL / 文件服务 / 模型运行由学校控制。断网任务、外部请求和权限边界纳入验收。
学生 / C 端不用学校采购和管理员配置，也能快速开始提问、手写、复习与查看反馈。个人模式直接建立自己的课程上下文；iOS、Android、鸿蒙手写端与网页按同一任务契约接续。可以选择适合的公网模型服务或自托管模型；调用前明确数据传输范围。个人数据不默认进入学校班级或他人账户。
↳

“本地部署”解决什么，不能替代什么

让推理、数据库与原始笔迹留在学校控制域，可以减少学生数据发往外部商业 API 的需要；但它本身不自动等于合规。仍要做目的限定、最小必要、访问控制、留存期限、未成年人信息保护、学校选用审查和安全管理。现行个人信息保护法强调合法、正当、必要及最小范围；教育部发布的 JY/T 0661—2025《教育数据分类分级指南》自 2026-02-18 起实施。这里不把政策概括成“所有学生数据一律不得上云”。

09 / 竞品与选型

为什么做问侠，而不是直接接一个现成平台？

不是因为豆包、学而思或讯飞“没有模型 / 数据库 / 教学能力”。它们已有各自成熟的产品与解决方案。研究问题更窄：在同一套可审计的数学教学任务里，学校能否控制教学库、状态修订和模型部署边界，并用公开任务独立复现结果。

按公开交付边界比较
方案类型公开资料中的能力边界学校仍需核实的问题问侠研究的对照点
豆包 / 通用消费助手面向个人的问答、拍题或学习能力；具体功能以当前版本为准。学校能否控制题库 / 量规版本、学生事实的长期保存与退出、模型调用数据边界及班级复核流程？同题、同证据、同任务，对比步骤诊断、帮助暴露和可追溯修订；不把消费产品的便利性当成研究缺点。
学而思 / 好未来方案公开提供解题、题库和师生场景能力，并有平台 / API 入口。目标学校如何获得所需部署形态、数据访问权限、校本版本与完整成本；需按真实合同核验。比较教学对象可编辑性、来源版本、Agent 执行轨迹和系统任务基准；不预判其内部架构。
讯飞教育方案公开介绍智能批阅、错因与学情分析等教育产品能力。学校侧部署、数据迁移、校内模型替换、细粒度证据导出和采购条件需逐项询价核对。在相同作答和量规上做盲审，比较证据支持、教师纠错传播、可回放性与资源成本。
通用 Agent / RAG 平台可搭建企业 Agent 和检索增强流程，通用能力不局限于个人端。能否按高中数学对象与教学规则建模、支持私有环境、隔离评测集，并保持业务事务边界？给强通用模型配上合理数据库、Agent 和工具后共同对照，测系统任务而非裸模型聊天。
公开资料入口 豆包爱学功能文档 ↗ 好未来解题方案 ↗ 讯飞智能批阅方案 ↗ 百炼 Agent 能力 ↗
学校为什么用可以先核对数据控制域、课程 / 校本库修改权、迁移和退出能力、教师纠错链、离线任务与全量成本，再决定自建、采购或混合接入。问侠以可部署和可评测为研究目标，不预设学校一定要选自研。
学生为什么用个人端可以不等学校采购先开始使用；按作答步骤获得解释和后续练习，并保留自己控制的学习记录。帮助过程和独立表现分开，避免把“看过答案”误当掌握。

11 / 实施计划

先把数据和评分边界冻结，再扩模型与客户端

时间按申请书八个月路线整理。每个阶段都产出可回放工件；若数据审核、算力或教师参与未落实，后续指标如实顺延，不用模拟对话替代验收。

项目计划
第 1—2 月

教学数据与对象合同

选高中数学课程子集，建立 DB1 / DB2 / DB3 schema、来源与审核手册；联合校准首批题目、解法、操作与量规。

交付：发布子集、版本清单、双人复核与分歧记录。
第 3—4 月

答疑、状态与教师闭环

接通采集、检索、角色上下文、持久 Agent、事实事务、outbox、WikiPatch 与班级聚合；回放纠错和中途加入案例。

交付：端到端任务轨迹、恢复检查、权限与聚合验收。
第 5 月

冻结 Benchmark 与强基线

整理完整任务 episode、评分手册和封存分区；由标注者交叉评分、仲裁分歧；建立专项模型与通用 Agent 基线。

交付：封存任务集、评分器验证、一致性与基线报告。
第 6 月

模型适配与机制消融

在审核后的训练数据上适配 LoRA；测 4B / 9B / 27B，分别报告数据库、Loop / 上下文和 LoRA 的贡献。

交付：权重 / 配置清单、成本、延迟与断网任务报告。
第 7—8 月

多端回放与授权小规模试用

完成学生 iOS / Android / 鸿蒙手写采集，网页和教师封装端；开展获许可的试用、延迟复测和最终盲评。

交付：设备回放、净复核时间、学生独立表现与限制说明。
项目的研究主张

让小模型的边界可以被测出来，
而不靠更长的提示词来猜。

通过教学关系数据库、可恢复 Agent Loop 和人类校准的 LoRA 三条路线，重点验证 9B 能否覆盖定义好的完整教学任务；用 4B 寻找资源下限，用 27B 观察质量上限和难任务收益。答案交给封存 Benchmark 和真实教学记录。
